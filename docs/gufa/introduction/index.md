# 导读

> 写给 AI 时代的程序员
>
> 当代码越来越便宜，能看懂代码的人越来越贵。

## 一、AI 把代码写出来了，然后呢？

你大概已经经历过这样的下午。

你打开编辑器，向 AI 描述一个需求。它想了几秒，吐出一百多行代码。你复制，粘贴，运行，居然跑通了。你松了口气，继续下一个需求。

一个星期以后，这个功能出了点问题。你重新打开那个文件，发现变量名都很合理，注释也很完整，函数拆得比你平时还整齐。但是你看不懂。不是语法看不懂，是你说不清它为什么这样写：为什么这里要多一次拷贝，为什么那个缓冲区是 4096，为什么先排序再查表，为什么删掉某一行之后程序会慢十倍。

你只能再问 AI。它又给你一版。两版都能跑，你不知道该信哪一版。

这时候你缺的不是第四版代码，而是三个很土的问题：数据放在哪？每一步的代价是多少？出错的时候，程序会怎么坏？这三个问题，AI 也能回答，但它回答得对不对，得由你判断。判断的本钱，是你自己曾经一笔一画地把这些东西摆过一遍。

这不是 AI 的错。AI 只是把“写代码”这件事变便宜了。它没有，也不可能替你建立一套判断：什么样的代码是好代码，什么情况下该省，什么情况下不能省，资源不够的时候先砍哪里，出了问题从哪里看。

代码越便宜，判断越贵。这本书想谈的，就是判断。

它不打算把你训练成一台人形编译器，也不打算让你背完 C 语言的所有角落。它只想把写代码时最容易被跳过的那一层补上：程序跑起来之后，内存里到底发生了什么。你知道了这一层，再看 AI 生成的代码，就不是在看一堆咒语，而是在看一组可以检查、可以质疑、可以修改的决定。

## 二、好代码不是灵感，是约束逼出来的

很多人以为好代码来自聪明。来自某个高手在凌晨三点突然开悟，写下一段旁人看不懂、机器却跑得飞快的神迹。

不是的。

好代码大多数时候是被逼出来的。内存只有 64 KiB，逼你设计块头；没有动态数组，逼你想清楚容量怎么长；终端只有八十列，逼你把输出排得一行是一行；每一步都要能停下、能检查、能复现，逼你把“差不多”改成“说清楚”。

约束不是好代码的敌人，约束是好代码的模具。

我后来越来越觉得，好代码大概来自三样东西。第一是对问题的理解：你到底在解决什么，输入是什么，输出是什么，边界在哪里。第二是对约束的承认：内存有多少，时间有多紧，谁会来改，改坏了怎么发现。第三是对反馈的尊重：写完不算完，跑起来、打印出来、拿边界数据撞一撞，才知道自己写的是代码还是愿望。

这三样都不神秘，但它们都需要时间。AI 可以帮你省掉敲键盘的时间，省不掉你理解问题、承认约束、建立反馈的时间。有时候它还会把这三样一起省掉，直接给你一个“看起来能跑”的答案。

你今天用的框架替你做了很多决定：内存怎么给，数组怎么长，错误怎么抛，缓存怎么放。这些决定当然有价值，它们让普通人也能快速做出东西。但代价是，决定被藏起来了。你看见的是 `push`、`map`、`await`，看不见底下那一块内存正在被复制、被移动、被释放，或者正在悄悄泄漏。

于是你写得出功能，却说不清成本。功能能跑，成本失控，这在 AI 时代会变得越来越常见：代码生成得越快，失控得也越快。

这本书要把那些被藏起来的决定重新摆到桌面上。不是让你以后都不用框架，而是让你在用框架的时候，知道自己在用什么，知道它哪天会咬你，知道被咬之后从哪里下刀。

## 三、把库拿走，你还剩什么

这本书有一个很不合时宜的约定：不用动态内存库，不用第三方数据结构，不用图形库，不用机器学习框架。

没有 `malloc`，没有 `free`，没有 `std::vector`，没有现成的哈希表，没有现成的矩阵库。你只有变量、结构体、指针、连续数组，以及一块自己划出来的静态字节区。

听到这里，很多人会问：这不是自讨苦吃吗？都什么年代了，为什么不用现成的？

把动态内存库拿走，把框架拿走，把 AI 给的脚手架拿走，程序员还怎么活？这本书的回答很土：靠字节、地址和一块数组活。

因为现成的东西太多了，多到你已经忘了它们是怎么来的。

`malloc` 不是天上掉下来的。它背后是一个分配器：块头、空闲链表、对齐、拆分、合并、碎片。你天天调用它，却不一定知道“内存不足”到底发生在哪一步。数组不是天生会长的。它背后是容量、长度、增长因子和一次一次搬家。你天天用它，却不一定知道为什么一次 `push_back` 会突然慢下来。

把库拿走，不是为了证明你能吃苦，是为了让你看见这些决定。看见之后，你才有资格说“这个库不适合我”，而不是只会说“这个库不好用”。

举个例子。给你 64 KiB 内存，让你同时放一张字符表、一段文本和一台虚拟机的栈。你不能 `malloc`，不能扩容，不能把问题推给操作系统。你只能先量：每样东西最大需要多少，什么时候可以复用，哪一块必须常驻。量完再画块，画完再写代码。这个过程很慢，但它逼你把“大概够用”变成“算过，够用”。

现代开发很少这样干活。现代开发是“先跑起来，再说”。这句话有它的道理，产品要先验证，性能可以后补。但如果一个人从来只写过“先跑起来”的代码，他就不知道“跑起来”之后还有哪些账要还。这本书补的就是这笔账。

说它是程序员的保命葵花宝典，不是因为它有什么神秘招式，而是因为招式少到不会忘。断网了，没有包管理器了，换了一台机器，换了一个平台，甚至换了一个 AI 助手，你手里还有字节、地址和一块数组。只要这三样还在，你就能从零把东西重新搭起来。

这不是怀旧。古法编程的“古”，不是“旧”，是“少”。少到你能全部装进脑子里，少到出了问题你知道该看哪一行。

## 四、没有图，只有一行一行打出来的真相

这本书里没有一张图。

没有架构图，没有流程图，没有彩色方块和箭头，没有“一图看懂”。也没有截图，没有示意图，没有装饰性的插画。整本书只有四样东西：汉字、LaTeX 公式、C 语言代码，以及代码跑出来的字符。

为什么这么狠？

因为最早的程序员也没有图。他们在纸带上打孔，在电传打字机上敲命令，字球一下一下砸在纸面上，终端吐出一行又一行字。没有屏幕，没有鼠标，没有花花绿绿的界面。计算机最开始给人的全部反馈，就是一行字符。他们照样把操作系统、编译器、数据库和游戏造了出来。

那时候查错也没有断点窗口。程序错了，就把中间结果打在纸上；纸带断了，就用胶带粘起来重新穿；内存不够，就一个字节一个字节地抠。听起来很苦，但他们也在里面玩出了花：用字符画地图，用打印机的响声当音乐，用一行一行的输出调试一整个操作系统。限制没有让他们停止玩，反而让玩变得具体。

这本书想保留的就是这种具体。你敲下的每个字节都会有个去处，你打印的每一行都能对上某个地址。没有图可以躲，没有动画可以糊弄，错了就是错了，对了就是对了。

图当然好用。但图会撒谎，会省略，会把“这里还有一层”藏起来。字符输出不太会。地址就是地址，字节就是字节，`0x2a` 不会因为排版好看就变成别的数。你盯着十六进制表看久了，会开始对内存有感觉：哪一段是头，哪一段是数据，哪一块被踩了，哪一块从来没被写过。

比如一个最土的 `hexdump`：

```c
static void hexdump(const uint8_t *p, size_t n) {
    for (size_t i = 0; i < n; i++) {
        if (i % 16 == 0) printf("%08zx  ", i);
        printf("%02x ", p[i]);
        if (i % 16 == 15 || i + 1 == n) printf("\n");
    }
}
```

不到十行，没有颜色，没有图形，甚至没给你省掉对齐的麻烦。但它能告诉你：这一块内存里到底是什么。你把地址、字节和旁边的 C 变量一一对上，很多“玄学”就消失了。不是 bug 玄学，是你看不见它的地址。

所以这本书会教你写 `hexdump`，写块表，写虚拟机追踪器，写各种断言。这些当然是插桩，是给程序装仪表。但插桩不是目的。目的是让你在没有图的情况下，仍然能看见程序内部发生了什么。

一行一行打出来的真相，比一张漂亮的图可靠。

## 五、四步，把一台计算机搓出来

这本书不是按 C 语言语法目录组织的。它讲一个故事：如何把一台计算机，从一块连续数组里搓出来。

故事分四步。

**第一步，计算机里到底有什么。** 从字节和地址开始，讲变量为什么是一个区间，指针为什么能加减，数组为什么是连续的，结构体为什么有空洞。你会自己做一张“纸带台”，把一块内存摊开，标上地址、类型和值，像法医一样检查每一格。做到最后，`int` 不再是一个黑盒，而是一段有起点、有长度、有字节顺序的区间；指针不再是“存地址的变量”，而是可以算、可以比、但绝不能乱越界的地址。

第一步会把这件事写成一行很短的公式：

$$
\operatorname{addr}(a,i)=a+i\cdot s
$$

数组的第 $i$ 个元素，地址就是起点 $a$ 加上 $i$ 个元素大小 $s$。就这么一行，没有别的。你以后看到的切片、索引、迭代器、矩阵步长，很多都是从这个式子长出来的。

**第二步，计算机怎么管理。** 同一块内存，怎样同时变成字符串、表格、网格和结构体？你会自己写一个分配器：块头、对齐、首次适配、拆分、合并、碎片。然后你会发现，所谓“数据结构”，很多时候只是同一块字节的几种看法。分配器不是系统魔法，它只是一个人写的函数，只不过这个函数管着别人的命。你要让它分配得对、释放得干净、合并得及时，还要在块头被踩坏的时候有办法查出来。

**第三步，怎么在计算机里再造一台计算机。** 把一部分内存当指令，另一部分当数据，写取指、译码、执行的循环，写汇编器，写栈和函数调用。最后，你会在自己的虚拟机里，再解释另一段程序。机器里长出机器，这件事本身就很好玩。更好玩的是，你会发现“指令”没有神秘之处：它只是几个字节，碰上一个愿意解释它的循环，就变成了加法、跳转、函数调用和输出。

这本书还会再往前一步：让这台机器直接读懂一小片 C。不是调用外面的编译器，也不是把 C 翻译成宿主程序，而是把 C 源程序当成虚拟机内存里的一段字节，交给机器里的 `AletheiaC` 解释器。你在外层虚拟机里执行一条 `ALETHEIA_C` 指令，内层就开始跑 C：变量、数组、指针、`if`、`while`、函数、递归，全都在同一块数组里发生。用 C 写成的机器，最后能跑 C。这是整本书最像大力丸的一刻。

这台机器有一个正式名字：**Aletheia**。希腊语里的“不遮蔽”。工程上不再叫它别的名字，代码里的类型和函数都以 `Aletheia` 开头或结尾。它的中文诨名还是“大力丸一号”。

**第四步，计算机如何学习，如何高效地解决问题。** 搜索、排序、图、动态规划，然后是矩阵、神经网络、反向传播、梯度下降。最后把训练好的小网络量化，发射成自己设计的指令，放回自己造的虚拟机里跑。学习不是调包，最起码不全是；它是一串在数组上反复执行的循环，是一遍一遍算梯度、改参数，直到损失降下来。

这四步不是四门互不相干的课。它们是同一条流水线上的四道工序：先备料，再搭架子，再装传动，最后教它自己找路。你可以在任意一步停下来，手里都会多一个能用的零件；但只有走到最后一步，你才会看见整台机器是怎么转起来的。

更重要的是，它们共用同一块内存。第一步造出的数组，是第二步分配器的地基；第二步分配出的内存，是第三步虚拟机的房间；第三步造出的机器，是第四步学习算法的跑道。到了最后一卷的最后一章，你会把这些零件全部装起来：训练、量化、汇编、运行、输出，一台会学习的小计算机，从一块数组里站起来。最后，它还会在虚拟机里跑一段 C，证明这台机器不只认自己那套指令。

这台机器的全部内存只有 256 KiB，正好是第一卷那块 512 字节数组的 512 倍。指令、栈、分配器、C 解释器、神经网络，全都住在这一块数组里。机器内部不加载任何库：没有 libc，没有 libm，没有动态链接器，没有第二个运行时。需要什么，就自己写进机器里。这不是苦行，这是把“依赖”两个字重新变成可以看见的代码。

## 六、一章一个零件，最后一章总装

每一卷大约十章。前面几章不贪多，每章只做一个小组件，最后一章总装。

一章只解决一个能被验收的问题：字节怎么读写，块怎么对齐，空闲块怎么合并，指令怎么编码，栈帧怎么摆，梯度怎么回传。每章开头先做一个能看见结果的小实验，中间把实验写成公式和不变式，最后落成一个能编译、能运行、能检查的 C 程序。

每一章都给你四样东西：汉字讲解、LaTeX 形式化、可以单独粘贴的代码片段，以及一个完整的单文件程序。完整程序不是伪代码，不是“省略若干行”，也不是另存到别处的下载链接；代码就写在这一章的 Markdown 里，你复制到一个空文件里，敲一条 `cc`，就能跑出结果。代码块第一行会写好建议文件名，文件由你自己命名。

一章大概一万字，至少要有一个明确的形式化对象：一个定义、一条不变式、一个递推式，或者一条语义规则。公式不是摆着好看，每一个都要能指回代码里的某一行。你看见 $\operatorname{align}(n,a)=\lceil n/a\rceil a$，就应该能在代码里找到那个向上取整的表达式；你看见一条循环不变式，就应该能指出它在循环的哪一步成立、为什么退出时刚好给出答案。

每一章还会留下一个接口。下一章直接拿这个接口开工，不重复造轮子。第一卷留下一块能读写的字节区，第二卷在上面盖分配器，第三卷在分配器上盖虚拟机，虚拟机里再挂一个 `AletheiaC` 解释器，第四卷把学习算法塞进虚拟机。每一卷的最后是个大玩具，最后一卷的最后一章是总装：前面所有零件必须同时在场，少一个都装不起来。

总装不是把文件拼在一起，而是让它们真的互相咬合：学习程序要拿到分配器给的内存，虚拟机要执行汇编器生成的指令，量化后的权重要被当成数据读进去，最后的输出要能证明整条链路没有掉链子。到那一刻，你才会真正明白什么叫“系统”：不是几个模块放在同一个仓库里，是它们彼此依赖，拆掉一个就转不动。

这本书不是知识展柜，是工具箱。零件拆下来能单独用，装回去能跑整机。

## 七、这本书怎么读

如果你写过循环、函数、条件判断，会用终端，愿意照着敲、照着改、照着跑，就可以读。不要求学过 C，也不要求学过计算机组成原理。

但有一件事必须提前说：这本书不能只看。

你可以把代码复制下来，但你最好亲手敲一遍。你可以相信公式，但你最好拿一个小例子在纸上推一遍。你可以直接运行完整程序，但你最好故意改坏一处：把数组开小一格，把块头写错一位，把栈指针多减一次，看看程序怎么崩、断言怎么响、输出怎么变形。

看别人修车，和自己把手弄脏，是两回事。

我把读法分成三种。第一种是通读，先把四卷的故事看一遍，知道每一卷在造什么，不急着敲代码。第二种是跟做，打开终端，一章一章跟着写，每章至少把完整程序跑通，再故意改坏几个地方，看看断言和输出怎么反应。第三种是拆解，读完一卷之后，把那一卷的零件从零重写一遍，不看原文，只留接口，写完再对照。第一种花一个周末，第二种花几个月，第三种花多久，看你想把手弄多脏。

三种读法都行，但只读不做，最后大概只会剩下一种感觉：好像看懂了。感觉不值钱。能把一个块头写对，能把一个栈帧摆正，能把一个梯度算准，才值钱。

这本书也不适合所有人。如果你想找一本“七天精通某某框架”的书，它不是。如果你想找一本把现成库的调用方式抄一遍的书，它也不是。如果你只想要一个能跑的结果，不在乎结果为什么能跑，那 AI 确实比我写得快。

但如果你想在 AI 给出三个方案的时候，能说出哪个方案会在内存上出事；如果你想在系统半夜报警的时候，能沿着地址和字节一路查到根因；如果你想在资源不够、依赖不可用、文档缺失的时候，仍然能用手边最原始的材料把东西做出来。那么，这本书就是写给你的。

读完以后，你未必会变成一个更强的框架使用者。你更可能变成一个更难被糊弄的人。别人说“这里性能有问题”，你会问是内存带宽还是分支预测；别人说“这个抽象很好用”，你会问它底下拷贝了几次；别人说“模型学会了”，你会问损失怎么算、梯度怎么来、量化误差有多大。这些问题不一定每次都要问出口，但你心里得有地方放它们。

## 八、最后说一句

AI 时代最不缺的，是能生成代码的工具。最缺的，是能判断代码的人。

判断从哪里来？从你知道一块内存有多长，从一个指针为什么不能乱加，从一个分配器为什么要合并空闲块，从一条指令怎样变成一次状态转移，从一个梯度为什么要乘学习率。你亲手做过一遍，判断才有地方落脚。

计算机没有魔法。它只有字节、地址、循环，以及一层一层被解释的规则。你把最底下那一层看懂了，上面那些花里胡哨的东西，就都只是排列组合。

这也是为什么这本书里没有图。图是别人替你整理好的理解，字节是你自己看出来的理解。前者可以借，后者只能长。

所以，别急着打开框架文档。先打开终端，建一个空文件，写一个 `main`，打印一个字节。看看它的地址，看看它的十六进制，看看你写下的那个 `1` 在内存里到底长什么样。

大力丸不是补药。它是让你把手弄脏的东西。

那么，从[第一章 字节与地址](/gufa/ch1/)开始。起初，这块地是平的；我们先定义最小的颗粒，再给每一个颗粒一个位置。

如果你还想看这台机器造好之后能做什么，第二册《计算科学大力丸》的[导读](/jisuan/introduction/)接着写：机器搬到实验室中央，数学负责讲述，机器负责作证。
