# 字节与地址

> 第一章。零件：`AletheiaByte`。
>
> 在一个平的、什么都没有的世界里，定义最小的颗粒，并让每一个颗粒有位置。

## 一、起初，世界是平的

起初，这块地是平的。

不是一维的平，也不是二维的平。它没有刻度，没有格子，没有编号，没有名字。你把手放上去，摸不到边界，也摸不到中心。它只是空。

我面前的桌子上就有这样一块地。它是一块数组，256 KiB，262144 个字节。现在它还是空的，所有字节都是 0。没有变量，没有结构体，没有分配器，也没有机器。它不是一台计算机，至少今天还不是。它只是一块连续的地。

我给它起个名字，叫 Aletheia。名字是后来才有的，地是先有的。现在我还不打算给这块地画任何结构，因为一旦画了，你就会以为结构是天然的。结构不是天然的，结构是人画的。先看见平地，再看见画上去的线，你才会知道哪条线可以改，哪条线不能改。

计算机科学的世界，最先不是对象，不是类，不是框架，而是一块平的东西。你可以把这块地拉得很长，长到一眼望不到头，但它仍然是平的。平的意思不是简单，平的意思是还没有被划分。没有划分，就没有名字；没有名字，就没有东西可以指。

所以第一章要做的，不是造一台机器，也不是写一个漂亮的程序。第一章只做两件事：先定义这块地上最小的颗粒，再给每一个颗粒一个位置。颗粒有了，位置有了，后面才谈得上变量、数组、结构体和指针。

这就是我们的命题：在一个平的、什么都没有的世界里，怎么定义最小的颗粒，怎么在内存里找到它。

我先把话说在前面。我写这一章的时候，手里只有这块地。分配器、虚拟机、解释器，今天都不在桌上。我不知道它们以后会长成什么样，也不打算从未来借工具。今天能用的，只有字节、地址、一个循环和一台会打印字符的终端。

这已经够了。

我桌上的终端也是一块平的东西。它一次只肯显示一行字，字打完，纸就往前走一格。没有颜色，没有窗口，没有可以点的按钮。你要看什么，就让它打印什么；你要它打印得对，就得先把数据摆对。这个限制不是坏事。它逼着我把每一个字节都写清楚，把每一次失败都说明白，把每一行输出都当成证据。以后机器大了，输出多了，这个习惯还在。

因为如果连一个字节都不能可靠地读写，后面的东西全是空中楼阁。

## 二、第一颗粒：位与字节

我先问一个很笨的问题：内存里最小的是什么？

如果你去问硬件工程师，他大概会说，最小的东西是一个位。一个位只有两种状态，0 或者 1。它像一只开关，关上或者打开。八个位并排放在一起，就组成一个字节。

这个回答没有错，但它不是完整的回答。因为内存里最小的东西，和内存里能单独找到的最小东西，不是一回事。

位确实存在。一个字节里面就有八个位。你可以把它们打印出来，可以数它们，可以看哪一位是 1，哪一位是 0。但是，机器不会给每一个位单独发一个地址。你没有办法对机器说，请把 0x00008 号地址的第三位改成 1。机器只会说，0x00008 这个地址上有一个字节，你要么整个读走，要么整个写回。

这就是第一层区分：位是表示的最小单位，字节是寻址的最小单位。

这两句话要分开记。位回答的是“一个东西最少用几种状态才能表示”，字节回答的是“机器最少走一步能碰到多少东西”。前者是信息论的问题，后者是工程的问题。信息论说，一位就是一次二选一；工程说，一次二选一太小，不值得为它修一条完整的寻址通路。机器每一次访问内存，都要送出地址、选中单元、打开通路、把数据搬回来。这条通路有固定的成本，搬一位和搬八位，成本差不了多少。既然差不了多少，就一次搬八位。

这也是为什么“字节”这个词一开始并不等于八位。它只是“一口”的意思，一口能吃下多少位，各家机器自己定。六位的字节装得下大写字母和数字，装不下小写字母；七位的字节装得下 ASCII；九位的字节在一些大型机上出现过，多出来的一位用来做校验。八位不是从天上掉下来的，它是这些方案打了一架之后，剩下的那个公倍数。

在 C 语言里，最小的可寻址单位是字符类型。一个 `unsigned char` 占一个字节。我们今天不叫它字符，叫它字节。字节就是这块地上最小的颗粒。

一个字节有多少种样子？

八个位，每一位有两种可能，所以一个字节有：

$$
|\mathbb{B}|=2^{8}=256
$$

种样子。这里的 $\mathbb{B}$ 表示所有可能的字节值。它可以写成：

$$
\mathbb{B}=\{0,1\}^{8}
$$

也可以直接把 256 种值列出来，从 0 到 255。0 是一个合法的字节值，255 也是一个合法的字节值。0x00 表示八位全是 0，0xFF 表示八位全是 1。

不要小看这 256 个值。它不多，但它足够装下一个小整数，足够装下一个字符编码，也足够装下一组开关状态。你要表示更大的数，就把几个字节拼起来。那是后面的事。今天先承认一个字节只有 256 种样子，承认这件事，比记住 256 这个数字重要。

我把一个字节的八位打印出来，代码只有几行：

```c
static void aletheia_print_bits(AletheiaByte value) {
    int bit;
    for (bit = 7; bit >= 0; --bit) {
        putchar(((value >> bit) & 1u) ? '1' : '0');
    }
}
```

这段循环从最高位走到最低位。每一次，它把字节右移 `bit` 位，再和 `1u` 做按位与，得到当前这一位。如果这一位是 1，就打印字符 `1`；否则打印字符 `0`。

比如字节 0x41，打印出来是：

```text
01000001
```

这八位不是随便排的。它们有位置，也有权重。最右边那一位是第 0 位，权重是 $2^0=1$；往左一位是第 1 位，权重是 $2^1=2$；一直往左，第 7 位的权重是 $2^7=128$。一个字节的数值，就是所有为 1 的位的权重之和：

$$
b=\sum_{j=0}^{7} b_j 2^j,\quad b_j\in\{0,1\}
$$

你可以把这八个位想成八个格子，每个格子写 0 或者 1，每个格子上方标着它的价钱。最贵的格子值 128，最便宜的格子值 1。一个字节的值，就是所有写着 1 的格子的价钱加起来。这个算法和十进制数一模一样，只不过十进制每一位的价钱是 10 的幂，二进制每一位的价钱是 2 的幂。你会算十进制，就已经会算二进制，只是价钱表换了一张。

0x41 的八位是 01000001，按权重算：

$$
0\cdot128+1\cdot64+0\cdot32+0\cdot16+0\cdot8+0\cdot4+0\cdot2+1\cdot1=65
$$

65 正好是字符 A 的编码。这是历史留下的巧合，你先不用管它。你只要知道，0x41、65、01000001，说的是同一个字节，只是三种写法。

一个字节是一个整体。它不是八个可以单独寻址的小格子。你想改其中一位，必须先把整个字节读出来，改掉那一位，再整个写回去。比如要设置第 `bit` 位，可以这样：

```c
static AletheiaByte aletheia_set_bit(AletheiaByte value, int bit, bool on) {
    AletheiaByte mask = (AletheiaByte)(1u << bit);
    if (on) {
        return (AletheiaByte)(value | mask);
    }
    return (AletheiaByte)(value & (AletheiaByte)~mask);
}
```

`1u << bit` 造出一个只有第 `bit` 位是 1 的掩码。想置 1，就用按位或；想清 0，就把掩码取反，再按位与。这里没有魔法，只有位运算。你以后看到的标志位、权限位、压缩数据，很多都是从这几行长出来的。

这里还有一个小规矩：掩码用 `1u`，不用 `1`。`1` 是有符号整数，左移 31 位会碰到未定义行为；`1u` 是无符号整数，左移的规则清楚。我们今天只移 0 到 7 位，碰不到那个边界。但习惯要从现在开始，因为以后你会处理 32 位整数，边界就在眼前。

但注意，这段函数只改一个已经在手里的字节。它不负责找这个字节住在哪。找地址，是下一件事。

## 三、第一坐标：地址

有了颗粒，还要有位置。

一块地如果只有颗粒，没有编号，你仍然找不到东西。你知道地上有一个字节，但不知道是哪一个。你需要坐标。

我把这块地的每一个字节从 0 开始编号。0 号字节，1 号字节，2 号字节，一直到最后一个。地址就是编号。

这块地有多大？256 KiB。把它换算成字节：

$$
N=256\times1024=2^{18}=262144
$$

所以地址一共有 262144 个。编号从 0 开始，到 262143 结束。最后一个地址写成十六进制是 0x3FFFF。0x40000 不是这块地里的地址，它是再往后一个，已经出了边界。

地址集可以写成：

$$
A=\{0,1,\ldots,N-1\}
$$

$A$ 就是所有合法地址的集合。$N$ 是地址的总数，不是最后一个地址。最后一个地址永远是 $N-1$。这个差一，是后面无数越界 bug 的源头，今天就要把它写死。

地址是一个整数。它不是一个值，也不是一个内容。地址 0x00008 是一个位置；那个位置上放着什么，是另一件事。你把 0x41 写到 0x00008，地址还是 0x00008，变的是地址里的字节。你不能把地址和地址里的东西混为一谈。

地址从 0 开始，不是为了好看。假设第一个字节的地址是 1，那么第 0 个字节在地址 1，第 1 个字节在地址 2。你想算第 $i$ 个字节的地址，就要写 $1+i$。以后你想从某个起点走 $i$ 步，公式里就永远多一个减一或者加一。每一层抽象都要带着这个修正，错一次就够你查半天。

从 0 开始，第 $i$ 个字节的地址就是：

$$
\operatorname{addr}(i)=i,\quad 0\le i<N
$$

起点和偏移重合了。以后数组、指针、结构体偏移，全都靠这个重合活得轻松。你可以说这是人为约定，但它是一个很聪明的约定。

这个式子简单得不像话，但它是后面所有地址算术的地基。你以后写 `base + offset`，如果 `base` 是某个数组的起点，`offset` 是第几个元素，那么 `base + offset` 就是那个元素的地址。没有减一，没有加一。你以后写循环，`for (i = 0; i < n; ++i)`，走到第 `n` 个元素时正好停下，因为最后一个下标是 `n - 1`。这个 `n - 1` 和地址上界 `N - 1` 是同一个道理。

这个做法可以从 1945 年说起。那一年，冯·诺依曼参与的 EDVAC 报告草稿把存储器描述成一排编号的单元，指令和数据放在同一排单元里，靠编号去取。这个想法今天看起来平淡，在当时却是一个分水岭：存储器不再按内容分类，而是按位置编号。编号就是地址，内容可以是什么都行。我们这台小机器，走的还是同一条路。

地址用无符号整数，也有实际原因。地址没有负数。你不可能有一个负的门牌号。用无符号整数，地址加偏移不会变成负数，只会在超过上界时回绕。回绕听起来危险，但它至少是一个可以检查的边界。如果地址是有符号的，加一个偏移可能变成负数，负数再转成无符号去访问数组，结果是一个巨大的下标。两个错误叠在一起，比一个错误难查得多。

还有一件事要说清楚：在这个阶段，地址不是指针。

指针是 C 语言里的东西，它带着类型，带着算术规则，带着解引用。地址是机器里的东西，它只是一个编号。我们今天用整数表示地址，用数组下标访问字节。指针要等到后面再谈。现在你只要记住，地址是一个门牌号，门牌号本身不告诉你房间里住的是谁。

还有，0 号地址是合法的。它不是空。它是这块地的第一个字节。C 语言里的空指针常常写成 0，那是另一套约定。我们这里用 `AletheiaAddr` 表示地址，用返回值表示成功或失败，不用 0 表示失败。原因很简单：0 是一个完全合法的地址，不能拿它兼职做错误码。

## 四、第一张地图：地址空间

现在我们有颗粒，也有坐标。接下来要把它们连起来。

内存不是一堆散落的字节，而是一张从地址到字节的映射。给你一个合法地址，内存告诉你那个地址上是什么字节。这个关系可以写成：

$$
\mathcal{M}:A\rightharpoonup\mathbb{B}
$$

$\mathcal{M}$ 是内存，$A$ 是地址集，$\mathbb{B}$ 是字节值集。箭头上的那个小钩表示部分函数。部分函数的意思是，不是每一个输入都有输出。对 $A$ 里面的地址，$\mathcal{M}$ 给出一个字节；对 $A$ 外面的整数，$\mathcal{M}$ 没有定义。

为什么明明数组里每个格子都有值，还要写成部分函数？

因为数学上的内存和接口上的内存，不是同一个东西。数组确实对 0 到 262143 的每个地址都存了一个字节，静态数组启动时全是 0。可是接口不能假设调用者一定传一个合法地址。调用者可能传 0x40000，可能传 0xFFFFFFFF，可能传一个算错了的偏移。对这些整数，内存没有对应的字节。接口必须承认这件事，并且拒绝它。

所以我把 $\mathcal{M}$ 写成部分函数。它不是故弄玄虚，它是在模型里给“地址可能无效”留一个位置。模型里留了位置，代码里才会记得写边界检查。

有人会问，为什么不把 $\mathcal{M}$ 写成全函数，给非法地址规定一个特殊返回值？因为这条路走不通。字节的 256 种值全都合法，你找不到一个空位来放“错误”。用 0 当错误，0 本身就是合法字节；用 255 当错误，255 也是合法字节；用一个额外的布尔量，那其实就是把部分函数拆成了值和状态两部分，绕了一圈又回来了。既然 256 个值都被占满，最诚实的写法就是承认：有些地址没有对应的字节。

地图是有限的。有限的意思是，$\mathcal{M}$ 的定义域只有 262144 个点，不多不少。你不必考虑“地址空间之外还有什么”，因为地址空间之外没有东西。一个整数如果不在 $A$ 里，它就不是地址，只是一个碰巧长得像地址的数。这个区分很重要：不是所有 32 位整数都是地址，只有落在 $[0, N)$ 里的才是。

读一个字节，就是问这张地图：

$$
\operatorname{peek}(a)=\mathcal{M}(a),\quad a\in A
$$

写一个字节，就是改这张地图：

$$
\operatorname{poke}(a,b)\Rightarrow\mathcal{M}'=\mathcal{M}[a\mapsto b]
$$

$\mathcal{M}[a\mapsto b]$ 的意思是，新地图 $\mathcal{M}'$ 除了地址 $a$ 变成 $b$ 以外，其他地方都和旧地图一样。读是查询，写是更新。两个动作都很小，但它们是后面所有内存操作的原型。

一个地址是否合法，写成：

$$
\operatorname{valid}(a)\iff 0\le a<N
$$

这个式子看起来太简单，简单到不像公式。但它是第一道法律。没有它，`peek` 和 `poke` 就只能相信调用者；有了它，越界会变成一个明确的失败，而不是一次悄悄的踩内存。

这张地图是平的。

平的意思是，所有地址都在同一层。没有哪一段地址天然比另一段高贵，没有目录，没有树，没有“先找页再找块再找槽”。你给一个编号，地图就还你一个字节。地址空间是一维的，从 0 排到 $N-1$。你可以把它想成一条很长很长的纸带，每一格一个字节。

平有平的好处。规则少，算术简单，任何一段字节都可以用起点和长度描述。平也有平的代价。没有结构，所有结构都要你自己建。变量、数组、结构体，都是后来在这张平地图上画出来的。画得对不对，要看你有没有守住地址和边界。

这一章先把地图铺平。后面再往上盖东西。

本章先立下几个记号，后面只增不改：

- $\mathcal{M}$：内存映射。
- $A$：合法地址的集合。
- $\mathbb{B}$：字节值的集合。
- $\operatorname{peek}$：读一个字节。
- $\operatorname{poke}$：写一个字节。
- $\operatorname{valid}$：判断地址是否合法。

记号不是装饰。你看到 $\mathcal{M}[a\mapsto b]$，就应该能想到 `aletheia_mem[addr] = value` 这一行；你看到 $\operatorname{valid}(a)$，就应该能想到 `addr < ALETHEIA_ADDR_MAX` 这个判断。

## 五、为什么把世界铺平

现在要回答一个更硬的问题：为什么偏偏是这样铺？

为什么一个地址对一个字节，而不是对一个位，或者对一个字？为什么地址从 0 开始，而不是从 1 开始？为什么地址空间是平的，而不是分成一段一段？为什么是 256 KiB，而不是更大或者更小？

这些问题没有一个是自然规律。它们都是设计选择。设计选择就有历史，有代价，也有别的可能。

先说字节。

早期的计算机并不是一开始就统一用八位字节。六位、七位、九位都出现过。一个字节最初只是“一组位”，这组位用来表示一个字符或者一小段数据，具体几位，看机器。1956 年，IBM 的沃纳·布赫霍尔茨在讨论 Stretch 计算机时提出 byte 这个词，那时它还没有被钉死成八位。后来，IBM 的 360 系列把八位字节和按字节编址做成整个产品线的共同基础，八位才慢慢变成大家默认的答案。

为什么八位赢了？

因为它够用。八位有 256 种状态，装一个七位字符编码还有余量，装一个小整数也够，分几个标志位也够。它是二的幂，对齐、拆分、移位都舒服。它不大不小，刚好卡在一个工程甜点上。你可以说这是历史的偶然，也可以说这是无数工程妥协之后剩下的那个数。反正它不是上帝规定的。

ASCII 是七位的，理论上一个字节装得下 ASCII 还剩一位。可这多出来的一位并没有浪费。它后来被用来装校验位、装扩展字符、装各种语言的编码。八位像一个稍微大一点的抽屉，你一开始只放七件东西，后来发现第八件也用得上。工程上很多选择都是这样：不是先有需求再有尺寸，而是尺寸先松一点，需求自己会长出来。

你可以做一个思想实验：如果字节是九位，会怎样？一个字节有 512 种值，地址还是那些地址，数组还是那个数组。读写函数几乎不用改，把 `AletheiaByte` 换成九位无符号类型就行。可是终端打印会变，位运算会变，所有假设“八位”的代码都要重写。八位之所以重要，不是因为它比九位更真，而是因为所有人都同意了它。标准的力量，在于它让不同的人写出可以互相读懂的字节。

那为什么按字节编址，而不是按位编址？

因为位太小。大多数数据不是单独一个位，而是一个字符、一个小整数、一组标志。如果每个位都有一个地址，地址要多出几位，读写要多一套选择逻辑，内存也要多一堆线路。你为了改一个位，先要算它在哪个字节里，再算它在字节里的第几位，最后还是回到字节。既然最后都要回到字节，不如一开始就让字节当最小的寻址单位。

那为什么不是按字编址？

按字编址的机器也有。一个字是机器一次运算习惯处理的宽度，可能是一个字节，也可能是四个字节、八个字节。按字编址的好处是，取一条指令或者一个整数很顺手。坏处是，处理字符串和任意字节流很别扭。你想读一个字符，机器却给你一整个字，你还得从字里把它抠出来。字节编址把字符和二进制数据放在同一条起跑线上，读一个字节就是读一个字节。这个选择对后来的文本处理、文件格式、网络协议影响很大。

所以，字节不是最小的东西。位才是。字节是最小的可寻址单位。这个区别，是这一章的第一个关口。

再说地址从 0 开始。

从 0 开始，是因为偏移。数组的第 $i$ 个元素，地址就是起点加 $i$ 个元素大小。如果起点是 0，公式就是 $i$；如果起点是 1，公式就是 $1+i$。后者每算一次都要记得那个 1。计算机里最贵的东西之一，就是让人和机器都记得一个没有意义的常数。能把它消掉，就消掉。

从 0 开始还有一个好处：地址和下标是同一个数。你看到 `aletheia_mem[8]`，就知道它离起点 8 个字节。你不需要在脑子里做减法。这个习惯会一直用到数组、结构体和指针。

再说平的地址空间。

我先把可能的方案摆一摆。地址空间可以分成段，每一段有自己的起点和长度，段内再编址；这就是分段。地址空间也可以切成固定大小的页，由页表把虚拟地址翻成物理地址；这就是分页。两种方案都比“一个整数直接当门牌号”复杂。分段要维护段表，分页要维护页表，访问一次内存可能要先访问一次表。复杂有复杂的好处：分段能保护，分页能换出，虚拟地址可以比物理内存大。但这些好处，都要等机器长大以后才用得上。

真实机器不一定这么平。早期机器有分段，有页，有各种边界。平有平的代价：你不能靠硬件帮你检查一个地址属于哪个对象，所有边界都要软件自己守。平也有平的好处：规则少，算术直接，任何一段连续字节都能用起点和长度描述。我们这本书要从零造机器，规则越少越好。先把平的地铺好，后面再在上面画格子。

平还有一层意思：地址是线性的，但线性不等于没有结构。数组是在线性地址上画出的等距格子，结构体是在线性地址上画出的不同宽度的房间，栈是从一头往另一头长的连续区间。这些结构都不是硬件给的，是软件约定的。约定写在代码里，就要有人守。我们这本书里的所有结构，最后都要落回“起点加偏移”这一件事。你只要记住起点和偏移，就能在任何一层把结构拆开。

最后说 256 KiB。

这个数不是随便拍的。$256\times1024=2^{18}$，地址刚好落在 18 位里。它够放下一台小机器要用的代码、栈、工作区和一点输出，又不至于大到打印一张地址表就要翻几十页。更重要的是，它有限。

有限不是缺陷，有限是计算科学的前提。内存无限，就不需要分配器；地址无限，就不需要边界检查；时间无限，就不需要复杂度。所有的取舍，都是从有限开始的。你今天只有 262144 个字节，所以你会认真数每一个字节。这个习惯，比记住 262144 这个数字重要得多。

256 KiB 还有一个好处：它小到可以整个放进一张表里看。你在终端里打印一段地址窗口，一次看十几个字节，就能知道这块地现在长什么样。真实机器的内存动辄几十 GB，你不可能一眼看完；你只能靠工具、靠采样、靠猜。我们的机器小，小到你可以把它当成一张纸，用眼睛一行一行看过去。这对学习是极大的方便。你可以亲手数出一个结构体占几个字节，亲手看见一次越界踩到了哪里。大机器上要借助调试器才能看见的东西，这里打印一下就看见了。

地址类型用 32 位无符号整数。18 位就够表示这块地，为什么不用 18 位？因为 C 没有 18 位整数类型。你可以用位域硬凑，但位域的对齐和字节序由实现决定，不适合做接口。32 位是标准类型里最接近又最宽裕的选择，多出来的 14 位不是浪费，它们是边界检查的余地：任何大于等于 262144 的 32 位整数，都能被同一个比较挡住。

地址类型是接口的一部分，不是宿主机的 `size_t`。`size_t` 的宽度看平台，今天 32 位，明天 64 位；地址类型必须稳定，不然同一段代码换一台机器就变了。

还要分清两个词：地址空间和物理内存。地址空间是机器能发出的编号的范围；物理内存是真正存在的存储。在这台小机器上，两者重合：地址 0 就对应数组第 0 个字节。真实机器上，两者常常不重合，中间隔着页表。我们现在让它们重合，是为了先把“编号到字节”这件事看清楚。等以后要造更复杂的机器，再在中间加一层翻译。

这些选择没有一条是天上掉下来的。它们都是人在有限条件下做的决定。你以后看到别的机器用不同的字节宽度、不同的编址方式，不要急着说谁对谁错。先问它为什么这样选，代价落在哪里。

我列这些，不是要你背历史年代。历史年代是查得到的，设计取舍是查不到的。你看到一个数，要能问出它为什么是这个数；你看到一条规则，要能问出它替谁省了事、让谁多写了行。问多了，你自己设计东西的时候，就不会把第一个想到的方案当成唯一方案。

## 六、第一对动词：读与写

现在把地图写成 C。

公式已经把读和写说完了。现在要让机器也能读和写。数学和代码之间隔着一层翻译：公式说“存在一个映射”，代码要问“这块地放在哪个数组里”。翻译得好，公式和代码一一对应；翻译得不好，公式是公式，代码是代码，两边各说各话。

先定义类型和那块地：

```c
typedef uint8_t AletheiaByte;
typedef uint32_t AletheiaAddr;

#define ALETHEIA_SIZE ((size_t)256 * 1024)
#define ALETHEIA_ADDR_MAX ((uint32_t)ALETHEIA_SIZE)

static AletheiaByte aletheia_mem[ALETHEIA_SIZE];
```

`AletheiaByte` 是字节。用 `uint8_t`，不用 `char`。`char` 在某些平台上是有符号的，0xFF 可能被解释成 -1。我们要的是 0 到 255，不要符号。`uint8_t` 正好八位，前提是平台提供这个类型；如果平台没有八位无符号整数，它就不会定义。我们这台机器有。

`AletheiaAddr` 是地址。用 `uint32_t`，不用 `size_t`。地址是机器接口的一部分，宽度要稳定。`size_t` 是宿主机的尺寸类型，跟着平台走。今天你在 64 位机器上写代码，明天换到 32 位，`size_t` 就变了。地址不能这样漂。

`ALETHEIA_SIZE` 是字节数，262144。`ALETHEIA_ADDR_MAX` 是地址上界，262144。注意，它不是最后一个合法地址。最后一个合法地址是 262143。上界是“再往后一个”，这样判断可以写成 `addr < ALETHEIA_ADDR_MAX`，不用每次减一。

`aletheia_mem` 是一个静态数组。它不在栈上，不靠 `malloc`，程序一启动就在那里。C 标准保证静态存储期的对象会被零初始化，所以这块地一开始全是 0。不是魔法，是语言规定。

然后写边界判断：

```c
static bool aletheia_addr_ok(AletheiaAddr addr) {
    return addr < ALETHEIA_ADDR_MAX;
}
```

一行。但这一行是全章最重要的防线。

`addr < ALETHEIA_ADDR_MAX` 表示地址必须严格小于 262144。0 到 262143 都合法，262144 不合法。如果你写成 `<=`，262144 就会被放进来，数组访问就越界一个字节。一个字节的越界，足够让程序在别的地方莫名其妙地崩掉。边界条件不要靠感觉，要写成上界，再用严格小于。

接着写读：

```c
static bool aletheia_peek_u8(AletheiaAddr addr, AletheiaByte *out) {
    if (!aletheia_addr_ok(addr) || out == NULL) {
        return false;
    }
    *out = aletheia_mem[addr];
    return true;
}
```

读一个字节，要回答两个问题：地址合法吗？输出指针有效吗？两个都通过，才把字节写进 `*out`，返回真。否则返回假，什么都不改。

为什么用 `bool` 加输出参数，不直接返回 `uint8_t`？

因为 0 到 255 都是合法字节值。你不能用 0 表示失败，也不能用 255 表示失败。失败需要一个单独的通道。`bool` 是状态，`out` 是值。值和状态分开，调用者才不会把一次失败当成一个字节。

为什么失败不直接崩溃？

因为崩溃不是接口。一个函数遇到坏地址就 abort，调用者没有机会处理。我们这本书后面会造机器，机器里会有坏指令、坏地址、坏输入。如果每个错误都直接崩，机器就没法继续跑。今天先让读和写返回假，失败是一个结果，不是一个事故。

写也一样：

```c
static bool aletheia_poke_u8(AletheiaAddr addr, AletheiaByte value) {
    if (!aletheia_addr_ok(addr)) {
        return false;
    }
    aletheia_mem[addr] = value;
    return true;
}
```

写不需要输出参数，因为它只改地图，不返回值。它也要先过边界。非法地址一律拒绝，绝不“写一点点试试”。

这一组函数都标了 `static`。`static` 在这里的意思是“只在这个文件里可见”。组件先把门关起来，等接口稳定了再决定开哪扇门。现在没有别的文件，标不标 `static` 都能编过；但标上以后，编译器知道你只在这个文件里用它们，可以做更激进的优化，也可以在你写错名字时立刻报错。习惯要从第一天养。

读函数的输出参数用指针，是因为 C 只有值传递。你传一个 `AletheiaByte` 进去，函数改的是副本，调用者看不见。要让它把结果送回来，只能传地址。这里传的是“存放结果的变量的地址”，不是“内存里的地址”。两个地址，两个层次，不要混。`AletheiaAddr` 是内存的门牌号，`AletheiaByte *` 是结果放在哪的门牌号。

到这里，`AletheiaByte` 的接口就有了：

- `aletheia_addr_ok`：判断地址是否在 $A$ 里。
- `aletheia_peek_u8`：读一个字节。
- `aletheia_poke_u8`：写一个字节。

整个组件只有一个地方判断地址是否合法。这个设计叫“单一入口”。所有读写都从这里过，所以只要这里是对的，所有读写都是对的；只要这里错了，所有读写都错。查 bug 的时候，你不需要满程序找边界判断，只需要看这一个函数。把规则收在一处，是把复杂系统变简单的第一步。

接口很小，但每一行都能对应前面的公式。`aletheia_addr_ok` 对应 $\operatorname{valid}(a)$；`aletheia_peek_u8` 对应 $\operatorname{peek}(a)=\mathcal{M}(a)$；`aletheia_poke_u8` 对应 $\mathcal{M}'=\mathcal{M}[a\mapsto b]$。

这就是形式化和代码之间的关系。公式不是装饰，公式是代码的骨架。

## 七、在纸上走一遍

现在拿一个最小例子，手工走一遍。

先把 0x41 写到地址 0x00008。调用：

```c
aletheia_poke_u8(0x00008, 0x41);
```

地址 8 合法，因为 $8<262144$。函数把 0x41 写进 `aletheia_mem[8]`。地图更新：

$$
\mathcal{M}'=\mathcal{M}[8\mapsto 0x41]
$$

然后读回来：

```c
AletheiaByte value = 0;
bool ok = aletheia_peek_u8(0x00008, &value);
```

地址 8 合法，`out` 不为空，`value` 变成 0x41，`ok` 为真。0x41 的八位是 01000001。最高位是 0，权重 128 不参与；第二位是 1，权重 64 参与；最低位是 1，权重 1 参与。加起来是 65。这个值不是从空气里来的，它是八个位的加权和。

读回来和写进去相等，这个性质叫“往返一致”。它是内存最基本的契约。你写进去一个字节，读出来还应该是那个字节；如果没有别人改它，它就不该变。听起来像废话，但后面所有的数据结构、文件系统、数据库，都建立在这条废话上。今天先把这条契约用一个小例子钉住。

再写一个 0xFF 到地址 0x0000A：

```c
aletheia_poke_u8(0x0000A, 0xFF);
```

0xFF 的八位是 11111111，十进制是 255。它是这个字节能表示的最大值。再加一，会怎样？

在数学里，$255+1=256$。在这个字节里，256 装不下。`uint8_t` 的赋值会把结果截到低八位，于是：

$$
(255+1)\bmod 256=0
$$

再读回来，值是 0。这不是错误，这是字节的边界。你以后做计数器、做哈希、做校验和，都会碰到这个回绕。回绕不是意外，是有限位宽的必然。

样例里前八个字节是用 `addr * 17` 填的。为什么乘 17？因为 $17=16+1$。一个字节乘 16，相当于左移四位；再加自己，低四位和高四位就一样了。于是 1 乘 17 是 0x11，2 乘 17 是 0x22，一直到 7 乘 17 是 0x77。你在终端里看到 11、22、33、44、55、66、77，不是巧合，是十六进制的乘法表在说话。用这样的数填样例，有一个好处：如果哪一行错位了，你一眼就能看出来。

再看越界。

最后一个合法地址是 262143，十六进制 0x3FFFF。读它，合法。再往后一个，262144，十六进制 0x40000。它不在 $A$ 里，因为：

$$
\operatorname{valid}(0x40000)\iff 0\le0x40000<262144
$$

右边不成立。`aletheia_peek_u8` 返回假，`aletheia_poke_u8` 也返回假。数组没有被碰，程序也没有崩。这就是边界检查的意义。

现在看几个常见的错法。

第一个错法，把 `<` 写成 `<=`：

```c
return addr <= ALETHEIA_ADDR_MAX;
```

这样 0x40000 也会被当成合法地址。`aletheia_mem[262144]` 越过数组末尾一个字节。C 不会替你检查这个下标，它只会按地址算过去。结果可能是覆盖了别的变量，可能是段错误，也可能什么都没发生。最可怕的不是崩溃，是它看起来还在跑。

第二个错法，用 0 表示失败：

```c
AletheiaByte aletheia_peek_u8_bad(AletheiaAddr addr) {
    if (!aletheia_addr_ok(addr)) {
        return 0;
    }
    return aletheia_mem[addr];
}
```

调用者拿到 0，不知道这是地址里的真值，还是失败。0 是合法字节，不能兼职错误码。值和状态必须分开。

第三个错法，直接绕开函数：

```c
AletheiaByte value = aletheia_mem[addr];
```

这行代码没有边界检查，也没有失败通道。它把整个组件的防线拆掉了。你可以说“我自己知道地址合法”，但下一章、下一个函数、下一个读你代码的人，不一定知道。接口之所以是接口，就是因为它替所有人守住同一条规则。

第四个错法，把地址从 1 开始。

假设 0 号字节的地址是 1，那么 `aletheia_mem[0]` 的地址是 1，`aletheia_mem[1]` 的地址是 2。你写一个循环，从 0 走到 262143，每次都要加一才是地址。你在某个地方忘了加，整个表就错一位。错一位的表，比没有表更难查，因为每一行看起来都合理。

所以从 0 开始，不是美学，是减少错误。

还有一个不算错法、但值得说清楚的细节：`aletheia_print_window` 里的地址是 `base + (AletheiaAddr)i`。`base` 是起始地址，`i` 是第几个字节。因为地址从 0 开始，又是按字节编址，所以加 `i` 就是加 `i` 个字节。如果以后一个元素占四个字节，这里就要加 $4i$。地址算术的单位永远是字节，不是元素。这个规则现在看起来理所当然，等你写结构体的时候，会因为它省下很多麻烦，也会因为它犯下很多错误。

## 八、把 AletheiaByte 拼起来

现在把前面的片段拼成一个完整程序。

这个程序只做一件事：在一块 256 KiB 的静态字节区上，演示读写、边界和回绕。它不分配内存，不调用外部库，不生成任何图像。它只打印字符。

代码块第一行是建议文件名。你把它复制到一个空文件里，按这个名字保存，就可以编译。

```c
/* aletheia_ch01.c */
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>

#define ALETHEIA_SIZE ((size_t)256 * 1024)
#define ALETHEIA_ADDR_MAX ((uint32_t)ALETHEIA_SIZE)

typedef uint8_t AletheiaByte;
typedef uint32_t AletheiaAddr;

static AletheiaByte aletheia_mem[ALETHEIA_SIZE];

static bool aletheia_addr_ok(AletheiaAddr addr) {
    return addr < ALETHEIA_ADDR_MAX;
}

static bool aletheia_peek_u8(AletheiaAddr addr, AletheiaByte *out) {
    if (!aletheia_addr_ok(addr) || out == NULL) {
        return false;
    }
    *out = aletheia_mem[addr];
    return true;
}

static bool aletheia_poke_u8(AletheiaAddr addr, AletheiaByte value) {
    if (!aletheia_addr_ok(addr)) {
        return false;
    }
    aletheia_mem[addr] = value;
    return true;
}

static void aletheia_print_bits(AletheiaByte value) {
    int bit;
    for (bit = 7; bit >= 0; --bit) {
        putchar(((value >> bit) & 1u) ? '1' : '0');
    }
}

static void aletheia_print_row(AletheiaAddr addr, AletheiaByte value) {
    printf("0x%05x  %02x  %3u  ", (unsigned)addr, (unsigned)value, (unsigned)value);
    aletheia_print_bits(value);
    putchar('\n');
}

static void aletheia_fill_demo(void) {
    AletheiaAddr addr;
    for (addr = 0; addr < 8; ++addr) {
        (void)aletheia_poke_u8(addr, (AletheiaByte)(addr * 17u));
    }
    (void)aletheia_poke_u8(8, 0x41);
    (void)aletheia_poke_u8(9, 0x42);
    (void)aletheia_poke_u8(10, 0xff);
    (void)aletheia_poke_u8(11, 0x00);
}

static void aletheia_print_window(AletheiaAddr base, size_t count) {
    size_t i;
    printf("ADDR    HEX  DEC  BITS\n");
    for (i = 0; i < count; ++i) {
        AletheiaAddr addr = base + (AletheiaAddr)i;
        AletheiaByte value = 0;
        if (aletheia_peek_u8(addr, &value)) {
            aletheia_print_row(addr, value);
        } else {
            printf("0x%05x  --   ---  --------\n", (unsigned)addr);
        }
    }
}

int main(void) {
    AletheiaByte value = 0;
    AletheiaAddr last = (AletheiaAddr)(ALETHEIA_SIZE - 1);
    bool ok;

    aletheia_fill_demo();

    printf("ALETHEIA BYTE\n");
    printf("SIZE       : %u bytes\n", (unsigned)ALETHEIA_SIZE);
    printf("ADDR RANGE : 0x00000..0x%05x\n", (unsigned)last);
    printf("BYTE SIZE  : %u byte\n", (unsigned)sizeof(AletheiaByte));
    printf("\n");

    aletheia_print_window(0, 12);

    printf("\nREAD BACK\n");
    ok = aletheia_peek_u8(1, &value);
    printf("peek(0x00001) -> %s, value=%u\n", ok ? "true" : "false", (unsigned)value);
    ok = aletheia_peek_u8(8, &value);
    printf("peek(0x00008) -> %s, value=0x%02x\n", ok ? "true" : "false", (unsigned)value);

    printf("\nBOUNDS\n");
    ok = aletheia_peek_u8(last, &value);
    printf("peek(0x%05x) -> %s\n", (unsigned)last, ok ? "true" : "false");
    ok = aletheia_peek_u8(ALETHEIA_ADDR_MAX, &value);
    printf("peek(0x%05x) -> %s\n", (unsigned)ALETHEIA_ADDR_MAX, ok ? "true" : "false");
    ok = aletheia_poke_u8(ALETHEIA_ADDR_MAX, 0x7f);
    printf("poke(0x%05x) -> %s\n", (unsigned)ALETHEIA_ADDR_MAX, ok ? "true" : "false");

    printf("\nWRAP\n");
    (void)aletheia_poke_u8(12, 255);
    ok = aletheia_peek_u8(12, &value);
    printf("peek(0x0000c) -> %s, value=%u\n", ok ? "true" : "false", (unsigned)value);
    (void)aletheia_poke_u8(12, (AletheiaByte)(value + 1u));
    ok = aletheia_peek_u8(12, &value);
    printf("peek(0x0000c) -> %s, value=%u\n", ok ? "true" : "false", (unsigned)value);

    return 0;
}
```

编译命令：

```bash
cc -std=c99 -O2 -Wall -Wextra -pedantic -o aletheia_ch01 aletheia_ch01.c
./aletheia_ch01
```

这段程序有几个地方值得再看一眼。

`aletheia_mem` 是唯一的存储。所有读写都经过 `aletheia_peek_u8` 和 `aletheia_poke_u8`。`main` 里没有直接碰数组。这不是形式主义，是把边界规则收在一个地方。以后接口要加检查、加统计、加追踪，只改这两个函数，不用满程序找数组下标。

`aletheia_fill_demo` 只负责造几个样例字节。它不打印，也不做判断。打印是 `aletheia_print_window` 的事。读写、填充、打印分开，每一块都只做一件事。

`main` 里的 `ok` 每一次都接住返回值。你可以忽略返回值，但你不应该忽略。写失败和写成功，在调试时是两条完全不同的路。

`sizeof(AletheiaByte)` 打印出来是 1。这个 1 不是猜的，是类型保证的。一个字节就是一个字节。

每一处写操作前面都有一个 `(void)`，表示“我知道这个函数有返回值，我故意不看”。这不是必须的，编译器不会因为你不接返回值就报错。但写上去以后，读代码的人知道你是有意忽略，不是忘了。小地方上的意图，积累起来就是可维护性。

整份程序只有一个数组、一组读写函数和一段打印。没有动态分配，没有文件，没有网络，没有随机数。它的行为完全由代码决定。同样的输入，跑一万次，输出一模一样。这种确定性，是后面所有实验的前提。如果一台机器的输出每次都不同，你就没法判断一次失败是机器错了，还是运气不好。先把确定性立住，再谈别的。

## 九、真实输出与验收

程序跑起来，终端打印：

```text
ALETHEIA BYTE
SIZE       : 262144 bytes
ADDR RANGE : 0x00000..0x3ffff
BYTE SIZE  : 1 byte

ADDR    HEX  DEC  BITS
0x00000  00    0  00000000
0x00001  11   17  00010001
0x00002  22   34  00100010
0x00003  33   51  00110011
0x00004  44   68  01000100
0x00005  55   85  01010101
0x00006  66  102  01100110
0x00007  77  119  01110111
0x00008  41   65  01000001
0x00009  42   66  01000010
0x0000a  ff  255  11111111
0x0000b  00    0  00000000

READ BACK
peek(0x00001) -> true, value=17
peek(0x00008) -> true, value=0x41

BOUNDS
peek(0x3ffff) -> true
peek(0x40000) -> false
poke(0x40000) -> false

WRAP
peek(0x0000c) -> true, value=255
peek(0x0000c) -> true, value=0
```

第一段告诉你这块地有多大，地址范围到哪里，一个字节占几个字节。`SIZE` 是 262144，`ADDR RANGE` 是 0x00000 到 0x3ffff。最后一个地址是 0x3ffff，不是 0x40000。这个区别，就是边界。

第二段是地址窗口。每一行有四列：地址、十六进制、十进制、二进制。0x00008 那一行是 `41 65 01000001`。同一颗字节，三种写法。你可以从十六进制看到它的值，从十进制看到它的大小，从二进制看到它的八位。

第三段是读回。0x00001 里是 17，0x00008 里是 0x41。读出来的值和写进去的值一致。

第四段是边界。0x3ffff 能读，0x40000 不能读，也不能写。失败返回 `false`，程序继续跑。

第五段是回绕。0x0000c 先写 255，读出来是 255；再加一写回去，读出来是 0。255 加一变成 0，不是程序算错，是字节只有八位。

这份输出不是手画的，是程序跑出来的。你可以自己编译，自己跑，自己对照。程序输出确定，重复运行结果一致。它没有随机数，没有时间，没有外部输入。

验收不是口号，是清单。清单上的每一条，都要能在终端里看见，或者能用一条命令验证。看不见的验收，最后都会变成“我觉得应该没问题”。我不相信“我觉得”，我只相信输出。

验收项如下：

- `sizeof(AletheiaByte)` 等于 1。
- 地址范围是 0x00000 到 0x3ffff。
- 0x00008 写入 0x41 后能读回 0x41。
- 0xff 的八位是 11111111。
- 0x3ffff 是合法地址。
- 0x40000 是非法地址，读写都返回假。
- 255 加一回到 0。
- 编译零警告。
- 地址检查器无报错。
- 重复运行输出一致。
- 没有 `malloc`，没有第三方库，没有图像文件。

编译时用这套命令：

```bash
cc -std=c99 -O2 -Wall -Wextra -pedantic -o aletheia_ch01 aletheia_ch01.c
```

再用地址检查器跑一遍：

```bash
cc -std=c99 -g -fsanitize=address,undefined -fno-omit-frame-pointer \
  -Wall -Wextra -pedantic -o aletheia_ch01_asan aletheia_ch01.c
./aletheia_ch01_asan
```

两次输出应该一样。地址检查器没有报错，说明这段代码没有越界，没有未定义行为，没有在边界上偷偷踩一脚。

## 十、交给下一章

这一章只做了一件事：让一个字节有地址。

我们定义了字节，定义了地址，定义了地址空间，定义了读和写。我们守住了两个边界：地址必须小于 262144，失败必须和值分开。我们还在终端里看见了一个字节的八位、一个地址的范围、一次越界的拒绝、一次 255 加一的回绕。

这些都很小。但它们不是玩具。后面的分配器、虚拟机、C 解释器、神经网络，全部要经过这层字节读写。今天这条边界守不住，后面的机器就建在沙子上。

这一章没有回答“多个字节怎么放”，也没有回答“字节怎么解释成一个数”。那些是下一章的事。今天只把最小的一层钉死：一个地址，一个字节，一次读，一次写，一条边界。

下一章要拿走的接口是：

- `AletheiaByte`：一个字节。
- `AletheiaAddr`：一个地址。
- `ALETHEIA_SIZE`：这块地的字节数。
- `ALETHEIA_ADDR_MAX`：地址上界。
- `aletheia_addr_ok`：地址是否合法。
- `aletheia_peek_u8`：读一个字节。
- `aletheia_poke_u8`：写一个字节。

下一章的问题是：如果一个东西不是一个字节，而是四个字节、八个字节，甚至更多，它住在哪里？我们怎么用起点和长度，把一段连续字节圈起来，给它一个名字？

到那时，地址还是地址，字节还是字节。变的只是我们看这块地的方式。
